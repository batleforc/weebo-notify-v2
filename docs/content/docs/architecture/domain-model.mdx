Everything on this page lives in `notify-domain`: no database, no clock, no
network. It is the layer that decides what a notification *is*, and it is the only
one you have to understand to predict what the API will do with what you publish.

## A notification is an object with a life

```
open ⇄ working ──▶ closed(status) ──▶ reopenable
```

`status` is orthogonal to the lifecycle: `success`, `failure`, `warning`, `info`,
`cancelled`. A notification can be `open` *and* `failure` — an incident that is
known bad and still running.

### Two publishing shapes, and one field decides which

Whether you send a `state` field is the entire distinction, and it changes when the
notification is allowed to expire.

| You publish | You get | Retention starts |
| --- | --- | --- |
| with `state` | a **lifecycle** notification, born in that state | at closure |
| without `state` | a **simple** notification, born `closed(info)` | at creation |

The consequence worth remembering: **a notification that is still open cannot
expire.** A two-day incident stays visible for two days without anybody configuring
anything. A fire-and-forget `curl` ages from the moment it lands, which is what you
want from a message.

### Revisions, and who wins

Each write is an immutable revision. The server stamps a monotonic `seq` on arrival
and the current state is whatever the **highest `seq`** says — last write wins.
Concurrent publishers (CI retries, parallel jobs) therefore need no coordination
and there is no `If-Match` to get wrong. Nothing is discarded: the full history is
kept and doubles as the audit trail.

Absent fields on a revision inherit from the current head, so an update can be as
small as:

```json
{ "state": "closed", "status": "success" }
```

Actions are the exception — they are **replaced wholesale** on every revision, never
merged. Interactions already recorded stay attached to the notification, not to the
revision that offered the button.

### Reopening

A closed notification stays writable. A revision on it either amends the closure
(new `status`) or **reopens** it — the CI re-run pushing onto the same
`external_id`. Reopening suspends the retention clock again, and it restarts from
zero at the next closure. Amending a closure does *not* push the deadline back.

## Retention

The channel owns the policy: a default, an optional forced ceiling, and whether
unbounded retention is allowed at all.

- A `ttl` longer than the channel ceiling is **clamped and reported** in the
  response, not refused. A CI job should not fail because it wanted its build log
  kept a week longer than the operator allows.
- `ttl: "0"` means "keep forever" and is refused unless the channel opted in.
  A publisher cannot pin a channel's storage on its own.
- Durations are written the way people write them: `30s`, `5m`, `4h`, `7d`, `2w`.
  One unit per value; `1h30m` is not a thing. Values come back in the largest unit
  that divides evenly, so `7d` reads back as `1w`.

### Closing what nobody is attending to

Retention above is measured from closure, so a lifecycle notification that never
closes is never kept for a week — it is kept forever. That is not a hypothetical: a
publisher only has to crash once, and nothing in the notification says the difference
between "still running" and "abandoned in March".

So the channel also owns a `close_after`, and a background pass closes any lifecycle
notification that has gone that long without **activity**:

- a revision, and
- an interaction — an acknowledgement or a reply.

Receipts do not count. A `delivered` receipt is a client having it on screen, which
happens without anybody deciding anything; counting it would mean an inbox left open
in a browser tab keeps every notification in it alive.

The default is one week, including for channels created before the field existed —
defaulting those to "never" would leave untouched exactly the notifications this
exists for. `close_after: "0"` opts a channel out, which needs no operator blessing
the way `ttl: "0"` does: declining the convenience cannot pin anybody's storage.

The closure is **not** a revision. Nobody asked for it — it is the absence of anybody
asking — and authoring one would mean inventing a system principal that then exists
everywhere principals do. The last revision keeps saying what the publisher said, a
`closure` event says the server closed it, and the retention clock starts from there.
A publisher that comes back to life reopens it with its next revision, exactly as it
would after any other closure.

### Closing by hand

A person who holds `publish` or `manage` in the channel can close a live notification
too: the web's **Close notification** button, `POST /notifications/{id}/close`
([RFC 0004](/docs/rfc/0004-closing-a-notification-from-the-web)). It is the same kind
of closure as the server's — no revision, the publisher's content and buttons kept, a
`closure` event — except that it names the closer in `closed_by`. `publish` already
allowed deleting, which is stronger; `manage` gains exactly this, because a channel's
administrator is who its readers turn to when something is left open. A subscriber
cannot close. Closing a closed notification writes nothing, and the publisher's next
revision with a live `state` reopens it and clears `closed_by`.

Browsers that are not looking get a silent Web Push that replaces the alert on the lock
screen ("Closed by Alice"); a visible tab takes the closure from its stream. Native
clients learn it at their next sync.

## Where a notification comes from

Every notification is written by a **publisher**: a user, a service account, a
channel key or a CI job, through `POST` or the `PUT` upsert. A channel can also have
**sources** the server reads for it: the feeds of a managed channel
([configuration](/docs/ops/configuration#feeds), RFC 0002). A feed is not a new kind of
channel or of publisher. The leader polls it and publishes each new item through the
same upsert, as the service account the feed names, with the external id
`feed:<item key>`. So the channel's members, policy, quotas, push and sinks apply to
feed items exactly as to anything else that account publishes, and a channel that
grants `publish` to that account alone is a channel only its feeds write to.

What a source adds to the model is memory, not content: which items of each feed were
already seen, so that an item is published once, even after its notification has
expired and while it is still in the feed.

## Content hygiene

Every piece of publisher-supplied text is sanitised **at ingestion**, so every
surface — terminal, toast, browser — is protected once rather than each having to
remember.

Stripped from every text field:

- **ANSI escape sequences** (`CSI`, `OSC`, `DCS`/`SOS`/`PM`/`APC`, and the
  two-character forms), including their arguments. A title that clears your screen
  or repaints your prompt is the classic terminal injection.
- **Control characters** — C0, `DEL`, C1 — minus the whitespace a markdown body
  legitimately contains.
- **Bidirectional overrides and zero-width characters**, the "trojan source" family.

Not stripped: **raw HTML**. The body is markdown and HTML in it is inert by
contract, escaped at render time under a strict CSP. Stripping it here would eat
legitimate text like `3 < 4`.

`view` actions accept `http` and `https` **only**. `javascript:`, `file:` and custom
schemes are refused at ingestion, so they never reach a client at all — and clients
check again before opening.

## Interactions

`ack`, `reply` and `choice` are recorded on the server and read back by whichever
service is waiting on them. No device ever calls out to a third party on a
notification's behalf.

| Kind | Deduplication |
| --- | --- |
| `ack` | idempotent per (user, key) — clicking twice records once |
| `choice` | exclusive per (user, key), last pick wins |
| `reply` | none; replies are comments and accumulate |

An `ack` records a per-user acknowledgement for the publisher to read back; it closes
nothing. Ending a notification is the scoped act of [closing by hand](#closing-by-hand).

## Errors

Rejections carry a **stable `code`** in the `application/problem+json` body. Match
on the code, not on the message — the message is for humans and may be reworded.

| Code | Means |
| --- | --- |
| `field.missing` | a required field was absent |
| `field.empty` | present, but empty once sanitised |
| `field.too_long` | over the character ceiling for that field |
| `field.malformed` | right size, wrong shape |
| `collection.too_many` | too many actions, tags or options |
| `payload.too_large` | over a byte ceiling |
| `notification.revision_limit_reached` | 1 000 revisions; publish a new notification |
| `device.limit_reached` | `[devices] max_per_user` active devices; revoke one first |
| `ttl.infinite_not_allowed` | this channel does not allow `ttl: "0"` |
| `action.duplicate_key` | two actions share a key |
| `action.unknown_key` | no such action — usually a revision replaced it |
| `action.kind_mismatch` | interaction kind does not match the action |
| `action.unknown_option` | that `choice` does not offer that option |
| `action.url_scheme_not_allowed` | `view` links are `http(s)` only |
| `silence.duration_required` | a group-scoped silence must be time-boxed |
| `notification.gone` | deleted or expired; it accepts no further writes |

Adding a code is not a breaking change. Renaming one is.

## Two habits in the code

**Validation is a constructor, not a step.** There is no way to hold a `Content` or
an `Action` that has not been sanitised and bounds-checked — including one that came
back out of Postgres, because deserialisation runs the same validation as ingestion.
Storage is not a trust boundary we get to skip: a row written by last month's build
must still satisfy this month's invariants.

**Nothing in the domain panics.** `unwrap`, `expect` and `panic!` are denied
workspace-wide. A malformed payload has to become a 4xx, never a downed replica.
