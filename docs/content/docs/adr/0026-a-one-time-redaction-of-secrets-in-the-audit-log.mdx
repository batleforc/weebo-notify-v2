title: ADR-0026 — A one-time redaction of secrets in the audit log
description: Webhook urls journalled before sink ids were redacted are rewritten once, by a migration, to their origin and a keyless marker; the append-only rule becomes a database trigger, and the redaction records itself.
---

Status: **accepted** (2026-10-10) · Supersedes: — · Superseded by: —

## Context

The audit log is append-only (advisory SEC-P2-37): no code path updates or deletes
an entry, and `tests/audit_is_append_only.rs` holds the persistence crate to that.
Until now that rule was a convention and a source scan — nothing in the database
refused an `UPDATE`.

Webhook sink ids used to be `webhook:<url>`, and the reconciler journalled a managed
channel's declaration — `sinks[].url` included — into `detail.declaration` and
`detail.previous` of its `managed.channel.*` entries. Slack, Discord and Teams keep
their credential in that url's **path**. Sink ids are now
`webhook:<origin>#<fingerprint>`, the fingerprint an HMAC under the server-side
`[sinks] fingerprint_key` (`notify_ports::redact_url`). The server re-keys the queue
and the dead letters at boot, and `20261010200000_redacted_sink_ids.sql` redacted
the reconciler's snapshots. Neither touched the audit entries: editing history is
the one thing the log must not allow.

That leaves a live credential in a table that is kept forever, read by every
platform admin through `GET /admin/audit`, copied into every backup and every
`\copy` archive an operator takes ([Retention](/docs/ops/retention)). Rotating the
webhook is the real remedy, and operators should do it — but a log that keeps
handing out a secret after it is rotated is still a log that hands out secrets, and
one that is not rotated is a live one.

## Decision

**One sanctioned mutation, done once, by a migration:**
`20261010300000_redact_audit_webhook_urls.sql`.

- It rewrites `detail.declaration.sinks[].url` and `detail.previous.sinks[].url`
  for webhook sinks still in the old shape to **the origin and a keyless marker**,
  `https://hooks.slack.com#redacted`. Not the sink id's fingerprint: that is keyed,
  SQL never sees the key, and an audit entry records that a declaration changed,
  not where to deliver. A keyless digest was the first draft and was dropped — it
  can be brute-forced back to a url with a short token in it, offline, by anyone
  holding a backup. Nothing else in an entry changes — not `at`, not the actor, not
  the action, not the other sinks.
- It records itself: one `audit.redacted` entry, actor `configuration`, whose
  `detail` holds the number of entries rewritten and points here. A run that
  redacts nothing writes nothing.
- It turns the convention into a guard. `audit_entries` gains a trigger refusing
  `UPDATE` and `DELETE` (per row) and `TRUNCATE` (per statement). The migration
  disables the row trigger for its one `UPDATE` and re-enables it in the **same
  transaction**: `ALTER TABLE` is transactional and takes an ACCESS EXCLUSIVE lock,
  so no other session ever observes the table unguarded.
- It is idempotent — the redacted shapes (`#redacted`, and the keyed `#<hmac>` the
  reconciler now writes) have nothing after the origin, so a second run matches
  nothing — which is also what lets the conformance suite run it again
  against a planted old-format entry.

Any future mutation of the log needs its own ADR. This one does not set a precedent
for "a migration may edit history"; it sets the bar.

## Consequences

**Positive**

- The credentials stop being served by the admin API, and stop being copied into
  new backups and archives.
- The append-only rule is enforced by the database for every role that does not
  first, visibly, `ALTER TABLE … DISABLE TRIGGER` — a statement that takes
  ownership and shows up in `pg_stat_statements` and the server log.
- The redaction is in the log it redacted, with a count.

**Negative**

- The log is no longer byte-for-byte what was written. An investigator comparing a
  pre-upgrade archive with the live table finds the `url` fields differ in these
  entries; the `audit.redacted` entry and this record are the explanation.
- Redacted entries say only which origin a webhook pointed at: two webhooks on one
  host are indistinguishable in them, and the old url cannot be recovered from the
  log, by design. Entries written since carry the keyed fingerprint, which does
  change with the url.
- An operator's own retention trim ([Retention](/docs/ops/retention)) now has to
  disable the trigger inside its transaction, as that page shows.

**Accepted debt**

- Backups, archives and the structured-log mirror (`audit = true`) taken before the
  upgrade still hold the urls. They are outside the database's reach; rotating the
  webhooks is the remedy, and [Hardening](/docs/ops/hardening) says so.
- The trigger stops mistakes and the application's own role, not a database owner
  who means it. Revisit if the application ever stops connecting as the owner — a
  role without `ALTER` on the table would make the guard binding.
