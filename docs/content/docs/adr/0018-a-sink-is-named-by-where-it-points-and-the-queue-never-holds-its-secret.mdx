---
title: ADR-0018 — A sink is named by where it points, and the queue never holds its secret
description: Queue rows carry a sink reference; the target and its HMAC secret are resolved from the configuration at send time.
---

Status: accepted (2026-08-05) · Supersedes: — · Superseded by: —

## Context

Outbound sinks (§7.1bis) need a durable queue: a delivery has to survive a restart,
and it is retried on a published schedule for up to a day. So something has to be
written down. The question is *what*.

The obvious row holds the whole delivery, target included — that is what the port's
first draft did, with `SinkTarget` (URL **and** HMAC secret) inside `SinkDelivery`.
It is the shape that needs no lookup at send time, and it has three costs that only
show up later:

- the shared secret lands in the database, and therefore in every dump, every backup
  and every screen an operator can point at a row from. §6.1 deliberately keeps no
  application-level crypto at rest, which makes a third party's credential the one
  thing with no business being there;
- rotating the secret in the configuration would not reach what is already queued, so
  the rotation would be *mostly* applied — the worst kind;
- a sink removed from the configuration would keep being retried for a day at a place
  nobody serves any more.

The sink also needs an identity, and §11 gives it none: a `[[channels.managed.sinks]]`
block declares a `type` and a destination, and nothing else.

## Decision

**A queue row names its sink; it does not carry it.**

The identity is derived: `kind:destination` —
`webhook:https://hooks.weebo.poc/incidents`. It is stable across restarts, free of
credentials (a URL carrying userinfo is refused where the configuration is read), and
legible in a dead-letter listing, which is where an operator needs to know *which
endpoint* is stuck.

The target, with its secret, lives in a `SinkRegistry` built from the configuration at
boot and held in memory — the same standing as the trust policies of §5.3 and the push
transports of §11. The drain resolves it per attempt.

Two consequences are accepted rather than worked around:

- **a sink pointed at a new URL is a new sink.** Whatever was queued was destined
  somewhere else, and is dropped rather than redirected;
- **a delivery whose sink left the configuration is dropped, not buried.** A dead
  letter exists to be requeued, and there is nowhere left to requeue it to. It is
  logged, because silently discarding a delivery is the one thing a queue must never
  do quietly.

## Consequences

**Positive**

The secret exists in exactly one place, which is the file the operator already treats
as secret-bearing. A rotation applies to everything, including deliveries queued
before it. A dead letter can be shown to an admin without showing them a credential —
and, since the row's event is never served either, without showing them the content of
a channel they may not read (§5.4).

**Negative**

The drain does a lookup per attempt. It is a `BTreeMap` read in the same process, so
the cost is not the point — the coupling is: the queue is no longer self-contained,
and a delivery is only sendable while its sink is still declared. That is the property
above, stated as its own cost.

**Accepted debt**

The identity is a string with structure in it (`kind:destination`), parsed by
splitting on the first `:`. A future sink kind whose destination is not a URL or an
address — a Matrix room, a Slack channel — fits, but a kind that wanted *two*
destinations would not, and would need a real identifier in the configuration. That is
the change that would make us revisit this.
