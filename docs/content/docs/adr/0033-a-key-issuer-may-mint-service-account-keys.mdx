---
title: ADR-0033 — A key issuer may mint service-account keys
description: A token declared in config, presented without a person's session, may mint, list and revoke keys for managed service accounts and nothing else.
---

Status: proposed (2026-10-29) · Supersedes: — · Superseded by: —

## Context

Minting a key needs a person's session (`notify-app/src/keys.rs`: "a key
minting keys would outlive its own revocation"), and API keys and federated
tokens are never platform admin (`auth.rs`). That is right for people, but it
leaves a Kubernetes operator unable to hand a managed service account its key:
the only way today is someone logging in and pasting the secret into a
Secret.

The operator's v0.2 `NotifyApiKey` resource needs that path, and nothing else
from the API. "Operator" already names a person running the instance in these
docs, so the principal is a **key issuer**.

## Decision

**A token declared in config (`[[key_issuers]]`, read from a file or the
environment) may mint, list and revoke keys for managed service accounts. It
cannot mint keys for itself, for people, for channels or for dynamic service
accounts, reach any other route, or act as platform admin.** Every mint and
revocation it makes is audited under its own id.

- **Config:** `[[key_issuers]]` has an `id` (lowercase letters, digits and
  `-`, unique; the audit actor `key_issuer:<id>`) and a `token`, which must be
  an `env:NAME` or `file:/path` reference — an inline token is a structural
  error, since the file is a ConfigMap. The section is read at boot and is in
  `unreloadable`; the secret is resolved at boot, must be at least 32 bytes, and
  only its Argon2 hash is kept in memory.
- **Credential:** a static token, `Authorization: Bearer
  wki_<id>_<secret>`. Not a projected Kubernetes service-account token: notify
  does not depend on the Kubernetes API. Rotating it means changing the Secret
  and rolling the pods.
- **Authorisation, refused by default:** `Authenticate::execute`, which every
  route, stream and compat endpoint goes through, answers an issuer with `403
  credential.key_issuer_only`. Only the mint, list and revoke key routes call
  `execute_for_keys`, which admits it, and there the use cases bound it: a key
  for a service account whose origin is managed and which is active, with no
  scope in a channel that the account itself does not hold there; the keys of
  managed accounts only, listed and revoked. The issuer is a member of nothing,
  carries no groups and is never platform admin.

## Consequences

**Positive**

- A service account declared by a resource gets its key into a Kubernetes
  Secret with no human step, and loses it when the resource is deleted.
- A route added later refuses an issuer without knowing it exists.

**Negative**

- A credential that mints credentials now exists. Its reach is bounded to
  managed service accounts and to what they already hold, and revoking it means
  editing config and restarting, not the API.
- A leaked token is valid until the Secret is changed and the pods roll; it has
  no expiry of its own.

**Accepted debt**

- No per-issuer allowlist of service accounts: an issuer reaches every managed
  account. Revisit if a deployment runs more than one operator.
