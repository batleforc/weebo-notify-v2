title: ADR-0029 — Secret-key cryptography on aws-lc
description: JWT signing moves to jsonwebtoken's aws-lc backend and RFC 8291 encryption to a small module on aws-lc-rs, retiring web-push-native, p256 0.13 and the RSA advisory exception.
---

Status: **accepted** (2026-10-24) · Supersedes: the `rust_crypto` choice for `jsonwebtoken` (M1 audit) and the `web-push-native` choice (design §6.2) · Superseded by: —

## Context

RUSTSEC-2026-0387 (`crypto-bigint` < 0.7.6): subtraction, division and Montgomery
multiplication on *secret* integers could branch on their values, depending on
compiler and CPU. The fixed 0.7.6 has no 0.5 backport, and 0.5.5 reached us through
`p256` 0.13 by two paths:

- `jsonwebtoken`'s `rust_crypto` backend, which signs **ES256 with long-lived
  private keys** every time APNs or VAPID needs a token;
- `web-push-native` 0.5 (latest), whose RFC 8291 ECDH runs on an ephemeral secret per
  message.

Both operate on secrets, so the "unreachable" argument an exception needs does not
hold. The same backend also brought `rsa` and its RUSTSEC-2023-0071 exception.

The reason recorded for `rust_crypto` was "no C toolchain, for the image and the Tauri
cross-builds". Neither holds any more: the server already builds `aws-lc-sys` (for
rustls, through `rust-s3` and `hyper-rustls`), and the desktop/mobile client does not
depend on `jsonwebtoken` at all.

## Decision

- `jsonwebtoken` uses the `aws_lc_rs` backend.
- RFC 8291 encryption is `notify-push-webpush/src/encrypt.rs` (≈ 60 lines): ECDH
  P-256, HKDF-SHA256 and AES-128-GCM from `aws-lc-rs`, a fresh key pair and salt per
  message, one record. A test replays RFC 8291 Appendix A byte for byte; another
  pins the 4096-octet ceiling.
- `p256` 0.14 still parses VAPID and subscriber keys and renders public points;
  secret-key arithmetic is aws-lc's. The VAPID key is re-encoded to PKCS#8 DER before
  `jsonwebtoken` sees it, so SEC1 keys keep working on either backend.
- `.cargo/audit.toml` and `deny.toml` ignore nothing. `[bans].deny` lists
  `crypto-bigint` < 0.7.6, `rsa` and `web-push-native`, so either path coming back
  fails CI.

## Consequences

**Positive**

- RUSTSEC-2026-0387 and RUSTSEC-2023-0071 are closed, not excused; `cargo audit`
  reports no vulnerability.
- One crypto library for every secret-key operation of the server, and it is the one
  TLS already trusts. `Cargo.lock` loses ~490 lines (`p256` 0.13, `p384`, `rsa`,
  `elliptic-curve` 0.13, `web-push-native`).

**Negative**

- RFC 8291 is now our code. It is small and pinned to the RFC's own test vector, but
  a protocol bug is ours to find.
- aws-lc ECDSA is randomised where RustCrypto's was deterministic (RFC 6979): tests
  verify signatures instead of comparing them.

**Accepted debt**

- The `zbus` 5 stack under `notify-cli` (`notify-rust`, `keyring`'s Secret Service
  store) carries three *unmaintained* advisories (RUSTSEC-2026-0370..0372) with no
  upstream release on zbus 6 yet. Unrelated to this decision; tracked separately.
- Revisit if aws-lc stops being in the tree for TLS (then the C toolchain becomes this
  decision's cost again), or if a maintained RFC 8291 crate on a fixed stack appears.
