---
title: High availability
description: What statelessness buys, how live streams survive failover, and the single points of failure that remain.
---

**The API is stateless by construction.** All state lives in Postgres and the object
store; there are no server-side sessions, because authentication is pure JWKS
validation. No session replication, no sticky sessions — any replica serves any
request.

## Live streams across replicas

Each replica holds its own SSE and WebSocket connections. When anything is published,
the [event bus](/docs/adr/0008-postgres-listen-notify-as-the-default-eventbus) pokes
every replica, and each notifies its own connected clients.

Failover is invisible to the client: it reconnects — to any replica — with
`Last-Event-ID`, and the [global cursor](/docs/adr/0012-single-events-table-as-the-cursor)
guarantees no gaps and no duplicates. The bus only ever carries pokes, so a lost one
costs latency, never correctness: the cursor catches up.

## Background jobs run on the leader only

TTL purge, GitOps reconciliation, sink retries and DND digests run on a single
replica. Leader election is either a Postgres advisory lock (default, no extra
infrastructure) or the Kubernetes Lease API. When the lock is lost another replica
takes over; non-leaders keep serving the API normally.

## Rolling updates without a gap

Migrations are **expand/contract**: version N must run against version N+1's schema,
so the migration applies before the rollout. `/readyz` gates entry into the service.
On `SIGTERM` a replica **drains** — stops accepting connections, closes its streams
cleanly so clients reconnect elsewhere, and finishes in-flight requests within the
termination grace period.

## Remaining single points of failure

Stated plainly, because pretending otherwise helps nobody:

- **Postgres.** HA belongs to an operator (CloudNativePG, Patroni) — outside the
  application's scope.
- **The object store.** Same.
- **The identity provider is not one.** If Authentik is down, already-issued access
  tokens stay valid until they expire (JWKS is cached), and API keys and CI tokens
  are signed by us. Only *new* logins are unavailable — degradation, not an outage.
