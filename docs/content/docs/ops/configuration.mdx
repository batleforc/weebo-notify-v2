Configuration is layered, lowest priority first:

1. Built-in defaults
2. The TOML file (`--config`, default `config/dev.toml`)
3. `WNK_`-prefixed environment variables

## Every key is overridable, and that is tested

The mapping is mechanical: a path becomes `WNK_` plus the path joined by `__`.

```toml
[oidc]
issuer = "https://auth.weebo.poc"    # WNK_OIDC__ISSUER
```

This is not a convention we hope holds. **A generated test walks the entire
configuration schema and asserts that every key, without exception, is overridable
this way.** Adding a key that is not reachable from the environment fails CI.

That property is what makes a single `config/dev.toml` work under Docker Compose and
inside an Eclipse Che workspace, where browser-facing endpoints must be public routes
rather than `localhost`. No second file, no `if env == che`.

## Database

```toml
[database]
url = "postgres://…"                 # WNK_DATABASE__URL — never printed (Debug shows [redacted])
max_connections = 16                 # refused below 10
migrate_on_start = true              # WNK_DATABASE__MIGRATE_ON_START
acquire_timeout = "5s"               # wait for a pooled connection, then fail
idle_timeout = "10m"
max_lifetime = "30m"
statement_timeout = "30s"            # Postgres statement_timeout per connection; 0 disables
idle_in_transaction_timeout = "60s"  # Postgres idle_in_transaction_session_timeout; 0 disables
```

`max_connections` has a floor of **10**: six leader jobs (purge, stale closure, DND
digest, sink drain, feed poll, reconcile) each hold a connection for as long as they lead — the
advisory lock lives on it — and four more is the least that still serves requests
while they do. A smaller value is refused at startup by name.

With `migrate_on_start = false` the server does not touch the schema; run
`notify-server migrate` (a Job or init container — it applies the migrations and
exits 0) first. A replica whose schema is behind its binary then **refuses to start**
rather than serve against it. Migrations run on a dedicated connection with
`statement_timeout` lifted, so a long one is not cut off by the request limit.

Like `url`, `[attachments] access_key`, `secret_key` and `token_secret` are secrets:
they never appear in a `{:?}` of the configuration.

## Reconciliation guard

```toml
[reconcile]
max_removals = 5             # WNK_RECONCILE__MAX_REMOVALS
allow_mass_removal = false   # WNK_RECONCILE__ALLOW_MASS_REMOVAL
```

A truncated file reads exactly like an operator deleting most of what they manage.
When one pass would archive, delete or disable more than `max_removals` managed
channels and service accounts, it applies the rest of the file, **refuses the
removals**, logs an error and counts `reconcile_removals_refused_total`. Set
`allow_mass_removal = true` for the one deploy that removes a lot on purpose, then
unset it. Re-declaring a service account a pass disabled re-enables it, but its API
keys **stay revoked** — issue new ones.

## Devices

```toml
[devices]
max_per_user = 20   # WNK_DEVICES__MAX_PER_USER
```

The most **active** devices one owner may hold, push and stream counted together.
Past it, `POST /devices` answers `422` with code `device.limit_reached`; revoking a
device frees its slot. A ceiling so a leaked session cannot enrol endpoints without
end, each one a push the fan-out pays for.

## Retention

```toml
[retention]
batch_size = 1000            # WNK_RETENTION__BATCH_SIZE
pass_budget = "20s"          # WNK_RETENTION__PASS_BUDGET
revoked_credentials = "90d"  # WNK_RETENTION__REVOKED_CREDENTIALS
# audit = "400d"             # WNK_RETENTION__AUDIT — unset: the audit log keeps everything
```

`audit` is off by default, and a value **under 90 days is refused at startup**
([ADR-0027](/docs/adr/0027-audit-retention-through-one-sanctioned-purge)). The
database refuses it again whatever the file says. Archive what it will delete
before you set it: [Retention](/docs/ops/retention#the-audit-log).

## Sinks

```toml
[sinks]
dead_letter_retention = "30d"   # WNK_SINKS__DEAD_LETTER_RETENTION — set at boot
fingerprint_key = "…"           # WNK_SINKS__FINGERPRINT_KEY — ≥ 32 bytes, set at boot
previous_fingerprint_keys = []  # WNK_SINKS__PREVIOUS_FINGERPRINT_KEYS — rotation only
```

A webhook is identified — in the queue, the dead-letter API, the audit log and the
logs — by its **origin plus a fingerprint** (`https://hooks.slack.com#4f1c0a9e2b7d3c58`),
never its full url: many consumers keep their credential in the path. The fingerprint
is an HMAC under `fingerprint_key`, so it cannot be brute-forced back to the url
without the key ([hardening](/docs/ops/hardening#a-webhooks-fingerprint-is-keyed)).
The key is **required as soon as one webhook sink is configured** — the server
refuses to start without it — and must be at least 32 bytes (`openssl rand -base64
48`); serve it from a Secret. `config/dev.toml` carries a public development key that
only a `[server] dev` instance will boot on. Rotating the url changes the fingerprint;
so does rotating the key, which is why it is only read at boot and has a
[runbook](/docs/ops/runbooks#rotating-the-sink-fingerprint-key). `[[channels.managed.sinks]]` and `[sinks.smtp]` are re-read on
`SIGHUP`. A delivery whose sink the draining replica does not know (a rolling deploy,
a reload that reached some pods first) is kept and retried later; only after the 24 h
retry window does it become a dead letter, saying why. Dead letters older than
`dead_letter_retention` are deleted by the leader's drain.

## Feeds

A managed channel can follow RSS 0.9x/1.0/2.0, Atom and JSON feeds
([RFC 0002](/docs/rfc/0002-channels-fed-by-rss-and-atom-feeds)). The leader polls each
one and publishes its new items into the channel as a service account you name, through
the same upsert the API uses: the account's grant, the channel's quota and the
attribution all apply as they would to that account calling `PUT`.

```toml
[[service_accounts]]
id = "bot-feeds"
display_name = "Flux RSS"          # what the inbox shows as the author

[[channels.managed]]
id = "veille-rust"

  [[channels.managed.access]]
  service_account = "bot-feeds"
  scopes = ["publish"]              # required: the poller publishes as this account

  [[channels.managed.feeds]]
  url = "https://blog.rust-lang.org/feed.xml"  # http(s) only; no user:pass@
  publisher = "bot-feeds"           # required, a [[service_accounts]] id
  every = "30m"                     # default 30m, from 5m to 24h
  tags = ["blog"]                   # added to every item; default none
  max_per_poll = 10                 # default 10, from 1 to 50
  allow_private_network = false     # default false: non-public addresses are refused
  lang = "en"                       # "en" or "fr": the "Open" label and summary title
```

What to expect:

- **The first poll publishes nothing.** It records what is already in the feed, and
  logs `feed primed` with the item count. Changing a feed's `url` makes it a new
  feed, which primes again.
- **Each new item is one notification**: its title, an *Open* link to the item, the
  feed's `tags`, and the feed as `group_key`. No body; priority and TTL come from the
  channel policy. An item is published once even if its notification is later
  deleted or expires while it is still in the feed.
- **More than `max_per_poll` new items** publish the newest `max_per_poll`, preceded by
  one summary notification, "*n* more items from *feed*", linking to the feed's site.
- **A later poll where every item is new** publishes nothing and counts
  `outcome="suspicious"`: a feed whose ids change on every fetch would otherwise flood
  the channel. If a busy feed outruns its window between polls, lower `every`.
- **Requests are conditional** (`If-None-Match`, `If-Modified-Since`), so an
  unchanged feed costs a `304`. A failing feed backs off, doubling up to 24 h, and
  honours a longer `Retry-After`.
- **What the server will fetch is bounded**: public addresses only (the name, every
  redirect and IP literals are checked), no `HTTP(S)_PROXY`, 20 s per fetch, 2 MiB
  after decompression, at most 3 redirects and never from `https` to `http`, and the
  first 200 entries. An instance whose only egress is a proxy cannot use feeds.
- A quota or a removed grant stops that feed's pass; the items it had chosen are
  published on later polls, each once. With a `publish_per_min` below
  `max_per_poll + 1`, a backlog drains a few items per pass.

Refused at startup and on `SIGHUP` (a refused reload keeps the running file), each
message naming the channel and `feeds[n]`: a scheme other than `http`/`https`,
credentials in the url, a non-public IP literal without `allow_private_network`,
`every` or `max_per_poll` out of range, the same url twice on one channel, a
`publisher` that is not a `[[service_accounts]]` id or holds no `publish` grant in the
channel's `access`, any unknown key in the table (`interval = "15m"` is an error, not
a silent 30m), and a feed declared without `[sinks] fingerprint_key`, which redacts
feed urls in the reconcile journal and the logs as it does webhook urls. A token in
the query string (GitLab's `feed_token`) is therefore never stored or logged in
clear. Each `allow_private_network = true` is logged as a warning at load.

Feeds can only be declared here. There is no API or UI for them: letting a channel
manager make the server fetch a url of their choice is the request forgery this keeps
out of reach. Per-feed state lives in `feed_state`, keyed on a digest of channel and
url; the row of a feed removed from the file is deleted a day after the last pass
that saw it, so a rolling deploy does not re-prime it.


## JSON webhook transforms

`[[transforms]]` maps a producer's own JSON to notifications on
`POST /api/v1/compat/json/{transform}/{channel}`
([RFC 0003](/docs/rfc/0003-json-webhooks-mapped-by-declared-transforms); the
producer side and examples are in [Clients → JSON webhooks](/docs/clients/compat#any-json-webhook)).
Keys marked *CEL* hold one expression over `body` (and `item` with `split`).

```toml
[[transforms]]
id = "mlab-news"              # [a-z0-9-], ≤ 64 chars; the path segment
channels = ["security"]       # required, non-empty, no wildcard
lang = "en"                   # "en" (default) or "fr": the "Open" label, the truncation marker
split = 'body.items'          # CEL, optional: a list; one notification per element
max_items = 20                # with split: default 20, ceiling 50; more is a 422
title = 'item.title'          # CEL, required: a string
title_fallback = "mlab news"  # when title fails or is empty; default: the id
body = 'item.source'          # CEL: a string, Markdown
link = 'item.url'             # CEL: an http(s) URL, becomes the "Open" button
external_id = 'item.id'       # CEL: a string or a number; absent: a digest of the element
group_key = '"mlab-news"'     # CEL: a string
tags = '["news"]'             # CEL: a list of strings
priority = '"high"'           # CEL: min | low | default | high | urgent
status = '"info"'             # CEL: success | failure | warning | info | cancelled
state = 'null'                # CEL: open | working | closed
ack = 'null'                  # CEL: a button label, or null for none
update = false                # default false: an element already published is skipped
raw = "off"                   # "off" (default) | "item" | "payload"
```

Refused at startup and on `SIGHUP` (a refused reload keeps the running set): an `id`
outside `[a-z0-9-]` or declared twice; `channels` missing, empty or holding an id that
does not parse; no `title`; an expression that does not compile (the error quotes
the column, and hints at CEL quotes when the source holds none); a variable other than
`body`, or `item` without `split`; a nested comprehension, or one whose step reads
anything but its own variable, or calls `matches()`; more than 16 reads of `body`,
`item` or a comprehension's variable in one expression; an expression nested more
than 32 levels deep (`1u+1u+…` included) or with brackets nested more than 32 deep
(brackets inside string literals, raw or not, do not count),
or over 4 096 characters; a `matches()` pattern that is not a
string literal or does not compile; a string literal that `priority`, `status` or
`state` can result in and is not one of their values (`"hihg"`); `max_items` out of
range or without `split`; `raw = "item"` without `split`; any unknown key in the table.
A misspelt `[[transform]]` table loads but is named at startup as not honoured.

`notify-server doctor` and the startup log name, as notes: a listed channel that is
not a managed one (fine for a dynamic channel), a transform with `raw` on, and one
without `external_id`.

Evaluation runs on at most one blocking thread per core; a request that finds every
slot busy gets `503` and `Retry-After: 1`, and a producer waits one second at most.

**Rollout.** Replicas adopt a `SIGHUP` one at a time, and a rolling deploy runs two
configs side by side, so a new transform answers `404` on pods that do not have it
yet. Add a transform through a rollout (the config Secret's checksum), and point the
producer at it only afterwards. `transform_info{transform,hash}` shows which
declaration each pod runs.
## Development instances

`[server] dev = true` (`WNK_SERVER__DEV`) declares a development instance, and is
the only thing that lets the server boot on the development stack's defaults — a
loopback `[oidc] issuer`, the `weebo:weebo` database. `config/dev.toml` sets it;
nothing else should. Without it, a config that forgot `[oidc]` or `[database]`
refuses to start rather than trusting whatever answers on localhost.

## Identity provider: the client

weebo-notify signs users in as a **public** OIDC client (Authorization Code + PKCE),
so the provider must allow the `authorization_code` and `refresh_token` grants.
Authentik 2026.8 and later only accept the grants listed on the provider, and an
unset list is empty: every login then fails with `invalid_grant` and the server log
says `Invalid grant_type for provider`. `dev/authentik/blueprints/weebo-notify.yaml` is
a working example; its `password` grant is there for the compatibility tests only.

The desktop app needs two more things from an instance it can be pointed at
(RFC 0001): the provider registers `http://127.0.0.1:1420/auth/callback` as a
redirect URI for the same client (the app signs in through the system browser and
a loopback listener), and `GET /api/v1/client-config` is reachable through the
ingress without a token. That route publishes the issuer, the client id and the
attachment origin, the same public values the web image puts in `env.js`. A
desktop build no longer needs any of this baked in: it asks for the server at
first launch, shows the identity provider it names, and confirms through a native
dialog before storing it.

## Identity provider: unverified email

```toml
[oidc]
trust_unverified_email = false    # WNK_OIDC__TRUST_UNVERIFIED_EMAIL
```

An individual `email` binding in a channel's access list goes to whoever logs in
with that address — so only an address the identity provider vouches for counts.
A token whose `email_verified` is not `true` (absent included) is accepted, but its
`email` is ignored: the user is not created with it, and no `email` binding matches
them. Most providers send the claim — check what yours sends for an address it has
not confirmed.

Set it to `true` only for an issuer that never sends `email_verified` **and** only
lets users hold addresses it has checked. Otherwise anyone who can register
`alice@example.com` at the IdP is handed Alice's bindings.

A token that omits `email` altogether (a client that asked for fewer scopes) leaves
the stored address alone. A token that **carries** an `email` the provider does not
mark verified clears it: the provider no longer vouches for any address. Upgrading
clears every stored address once; each comes back on that user's next login, if
verified — until then their `email` bindings report them as pending.

If two users end up holding the same address (case-insensitively), an `email`
binding on it binds **neither**, and the reconciler logs an error: bind by `oidc_sub`
instead.

## Identity provider: key-set staleness

```toml
[oidc]
jwks_stale_grace = "1h"    # WNK_OIDC__JWKS_STALE_GRACE
```

The issuer's key set is refetched once it is an hour old. While the issuer is
unreachable, the old set keeps verifying for `jwks_stale_grace` more, so a short IdP
outage does not log everybody out — and one request refreshes while the rest carry
on with the set they have.

The cost is the withdrawn-key window: a key the issuer removed (the response to a
compromised signing key) keeps verifying here for up to one hour plus
`jwks_stale_grace`, if the issuer is unreachable when the set expires. `0` closes
the window — the set is dropped on the first failed refetch — at the price of
refusing every login during any IdP blip, and of every request waiting on the
refetch rather than one. Raise it only if your IdP's outages are longer than its
compromises are likely.

## Personal API keys: group snapshot

```toml
[auth]
group_snapshot_ttl = "7d"    # WNK_AUTH__GROUP_SNAPSHOT_TTL
```

A personal API key carries no token, so the groups it reaches channels through are
the ones its owner last showed — remembered whenever they sync or enrol a device.
Once that snapshot is older than `group_snapshot_ttl`, the key keeps only its
owner's direct memberships until they come back.

This is the bound on how long a user removed from a group at the IdP keeps reaching
its channels through a key nobody revoked. Lower it for a tighter bound; the price is
that an owner who has not opened the app for that long sees their key lose its group
reach. Accepted range: `1h` to `90d`. Read at boot — a `SIGHUP` does not change it.

## GitOps: managed versus dynamic

Channels and service accounts can be **declared in the configuration**, and then the
file is their source of truth. At boot and on `SIGHUP` the server reconciles: it
creates what is missing, corrects drift in access, TTL and receipts, and archives or
deletes what has disappeared from the configuration according to `on_removed`.

Anything created through the API or the UI is marked **dynamic** and is never touched
by reconciliation. The UI shows a `managed` badge and makes GitOps-driven fields
read-only — so it is always obvious which of the two you are looking at.

A channel's `publishers` block is a trust policy **scoped to that channel**, and it
takes priority over the global `[[trust_policy]]` entries.

<Callout type="warn">
  The platform-admin role is declared **only** in configuration, under `[admin]
  oidc_groups`. No API path grants it. That is deliberate: a role that administers
  the instance should not be reachable by a request to the instance.
</Callout>

## Web Push

```toml
[push.webpush]
vapid_key_file = "/secrets/vapid.pem"   # a path, not the key
contact        = "mailto:ops@weebo.poc" # RFC 8292 `sub`
```

A **path** rather than the key itself, so it can be mounted from whatever the cluster
keeps secrets in without the key passing through a configuration file that gets
committed by accident. `contact` is not optional: push services refuse a VAPID
assertion without one, since it is how a relay reaches the operator of a server that
has started misbehaving.

Both are validated at startup. A key that is not P-256, a file that cannot be read,
or a contact that is neither `mailto:` nor `https://` stops the process — the
alternative is finding out because somebody's phone stayed silent.

Omitting the section entirely is a supported deployment, not a broken one: no
transport is registered, `GET /api/v1/push/webpush` answers `501`, and every push
degrades to a poke the client fetches over TLS. `[push.apns]` and
`[push.unifiedpush]` are parsed but not yet honoured — the server says so at startup
rather than dropping them silently.

<Callout type="info">
  Rotating the VAPID key invalidates every existing subscription, silently: the
  server starts, relays accept the new assertion, and pushes stop arriving on devices
  that subscribed under the old one. Plan a rotation as a re-subscription.
</Callout>

## CLI download

```toml
[cli]
binary_path = "/usr/local/bin/notify"  # where the Containerfile puts it
```

The shipped image already contains the `notify` binary, built from the same
commit as `notify-server` in the same build — so the two can never disagree on
version. Nothing serves it until this section names where it is: opt in, the
same "no default configuration is baked in" rule every other section here
follows.

Once configured, any authenticated caller (a user or a service account — no
extra scope) can fetch it:

```bash
curl -H "Authorization: Bearer $TOKEN" https://weebo.example/api/v1/cli -o notify
```

Omitting the section is a supported deployment: `GET /api/v1/cli` answers
`501`, same as any other unconfigured capability (`[push.webpush]` above,
`[federation]`). A path that is present but cannot be read stops the process at
startup rather than answering `501` for a reason nobody configured.

<Callout type="warn">
  Linux only, for now — the cross-platform artefact matrix (macOS, Windows,
  other architectures) is a later milestone. This route hands out whatever this
  server's own container platform is.
</Callout>
