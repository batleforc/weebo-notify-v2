title: Observability

---

Every replica serves `GET /metrics` in the OpenMetrics text format, beside `/healthz`
and `/readyz` and outside `/api/v1`. It is scraped by infrastructure, not called by a
client: it has no OpenAPI entry, and it is unauthenticated for the same reason the
probes are — a scraper is a pod in the same namespace, not a person with a token.

```yaml
# A pod annotation, or the equivalent ServiceMonitor.
prometheus.io/scrape: "true"
prometheus.io/path: "/metrics"
prometheus.io/port: "8080"
```

## What is published

Six families, and the names are the contract — they end up in dashboards and alert
rules living outside this repository, so a rename here breaks somebody else's pager.

| Family | Type | Labels | What it answers |
| --- | --- | --- | --- |
| `notifications_published_total` | counter | `channel` | How much is being published, and where |
| `push_delivery_duration_seconds` | histogram | `transport` | How long a push relay took to answer |
| `push_failures_total` | counter | `transport`, `reason` | Attempts that did not arrive |
| `sync_backlog_size` | histogram | — | How far behind clients are when they reconnect |
| `realtime_connections` | gauge | `transport` (`sse`, `ws`) | Streams this replica is holding |
| `sink_dlq_depth` | gauge | `channel` | Sink deliveries given up on |
| `background_job_last_success_timestamp_seconds` | gauge | `task` | When each background loop last completed a pass without error |
| `background_job_failures_total` | counter | `task` | Passes that failed **or panicked** |
| `reconcile_removals_refused_total` | counter | — | Reconcile passes whose removals the `[reconcile] max_removals` guard refused |
| `fanout_outbox_rows` | gauge | `kind` (`pending`, `dead`) | Device pushes still owed, and those given up on (ADR-0025) — leader only |
| `fanout_outbox_oldest_age_seconds` | gauge | — | Age of the oldest push still owed; minutes means the drain is not keeping up |
| `feed_polls_total` | counter | `outcome` | How feed polls ended: `ok`, `not_modified`, `refused_address`, `too_large`, `timeout`, `http_error`, `unparsable`, `suspicious`, `superseded`, `publish_refused` |
| `feed_items_total` | counter | `outcome` | Feed items `published` (summaries included), `summarised` into a summary, or skipped as `invalid` |
| `feed_failing` | gauge | — | Feeds whose last poll failed — leader only |
| `notifications_closed_total` | counter | `reason` | Live notifications closed without a revision: `manual` (a person, RFC 0004) or `stale` (`close_after`) |
| `transform_requests_total` | counter | `transform`, `outcome` | JSON webhook requests (RFC 0003): `ok`, `too_large`, `form`, `forbidden`, `unlisted`, `not_json`, `not_list`, `too_many`, `busy`, `timeout`, `internal`, `refused` (quota mid-way), `error`, `all_invalid`; an unknown id counts as `transform="_unknown"` |
| `transform_items_total` | counter | `transform`, `outcome` | Elements `published`, `skipped` (already there), `invalid`; fields that failed (`eval_error`); ids taken from a digest (`id_digest`); raw blocks cut (`raw_truncated`) |
| `transform_eval_seconds` | histogram | `transform` | One request's evaluation, the wait for a slot included |
| `transform_info` | gauge | `transform`, `hash` | `1` per loaded transform, under a digest of its declaration: two hashes for one id means pods on different configs |

Every background loop is supervised: a pass that errors or panics is logged, counted
in `background_job_failures_total`, backed off (5 s doubling to 5 min) and retried —
it never stops its loop or the others. A loop that stopped *working* therefore shows
as a timestamp that no longer moves, which is what `WeeboNotifyBackgroundJobStale`
alerts on. Leader-only tasks only move the timestamp on the replica that leads.

`reason` is a closed set — `expired`, `failed`, `unusable` — because a free-form one
would make an alert match nothing the day a transport words its error differently. A
delivery is not a failure and carries no `reason`, but it *is* timed: a transport that
only appeared in the latency histogram when it succeeded would make a graph that
improves during an outage.

`realtime_connections` is also the signal the [HPA](/docs/ops/high-availability)
reads, so how quickly it comes back down matters, and it differs by transport:

- **SSE** learns of a departure without anything being published. A client killed
  with nothing in flight was measured off the gauge **50 seconds later** — two
  keep-alive intervals, because the first write to a dead socket still succeeds.
- **WebSocket** only finds out by writing, and it writes when something is published.
  On an instance with no traffic, a dead socket stays counted until the next publish.

Read the gauge accordingly: it is "connections held, plus recent departures", not a
live count. Scale on a trend rather than on a single scrape.

## What is not published, on purpose

No notification, no user, no device, no push endpoint — no label anywhere is
unbounded. Somebody who can reach this endpoint learns how busy the instance is and
what its channels are called, and nothing else. That is a real exposure and it is
bounded deliberately.

<Callout type="warn">
  An ingress that publishes `/metrics` is a deployment mistake — the same one that
  publishing `/readyz` would be. Keep it inside the cluster.
</Callout>

## The dead-letter depth is the leader's answer

`sink_dlq_depth` is refreshed by the replica that led the last
[sink drain pass](/docs/ops/high-availability) and by nobody else. On a follower the
family is **absent**, not zero.

That is the honest reading: an absent series says "this replica does not know", and a
series reading zero says "nothing is stuck". Only the first is true on a follower.
Alert on the maximum across replicas rather than on any single one:

```promql
max(sink_dlq_depth) by (channel) > 0
```

## Writing an alert that survives an idle instance

A labelled family has **no series until something is recorded**. A freshly started
replica serves `sync_backlog_size` — no labels, so one series from the start — and
nothing else. A dashboard panel therefore reads "no data" rather than zero on an idle
instance.

This is the metrics client's model rather than a choice made here, and it is worth
knowing before writing the rule rather than after: reach for `absent()`, an `or
vector(0)`, or a `for:` window long enough to cover a quiet period.

## Alerts and dashboard shipped with the chart

`prometheusRule.enabled` in the Helm chart installs a `PrometheusRule` built on the
families above, each alert linking its [runbook](/docs/ops/runbooks) section:

| Alert | Expression, in short | Runbook |
| --- | --- | --- |
| `WeeboNotifyNoLeader` | `sink-drain` (the leader's 5 s loop) last succeeded > 2 min ago, or never | leader lock |
| `WeeboNotifyBackgroundJobStale` | `time() - max by (task) (background_job_last_success_timestamp_seconds)` > `jobStaleSeconds` | leader lock |
| `WeeboNotifyBackgroundJobFailing` | `increase(background_job_failures_total[15m]) > 3` | leader lock |
| `WeeboNotifySinkDeadLetters` / `…Growing` | `max by (channel) (sink_dlq_depth)` above `dlqDepth`, or rising for 30 min | dead letters |
| `WeeboNotifyPushFailureRatio` | `push_failures_total` / `push_delivery_duration_seconds_count` > `pushFailureRatio` | key rotation |
| `WeeboNotifyRetentionBacklog` | `max by (kind) (retention_backlog_rows)` > `retentionBacklogRows` for 1 h | retention |
| `WeeboNotifyDown` | no `up == 1` for the server Service | Postgres |
| `WeeboNotifyReadinessFlapping` | `kube_pod_status_ready` (kube-state-metrics) changing > 4× in 15 min | Postgres |
| `WeeboNotifyHttp5xx` | ingress-nginx `nginx_ingress_controller_requests` 5xx ratio > 5 % | Postgres |

Two gaps are deliberate rather than overlooked: the server publishes **no request
counter** (the 5xx rule reads ingress-nginx, and is off on other controllers via
`prometheusRule.http5xxFromIngressNginx`) and **no connection-pool gauge** — `/readyz`
checks Postgres, so readiness flapping is the pool/connectivity signal.

The job families label the job `task` (`purge`, `close-stale`, `dnd-digest`,
`sink-drain`, `feed-poll`, `fan-out`, `reconcile`) rather than `job`, which Prometheus already
attaches to every scraped series — a server-side `job` would be renamed
`exported_job` and every selector written against it would match nothing.

The feed families carry no feed or channel label, on purpose: feeds are unbounded in
number and a feed url may hold a token. A feed host being down is not an incident for
this instance, so the chart pages on nothing feed-related. A ticket-level rule is
worth adding yourself:

```yaml
- alert: WeeboNotifyFeedFailing
  expr: max(feed_failing) > 0
  for: 6h
  labels: { severity: ticket }
  annotations:
    summary: A feed has failed every poll for six hours; its `warn` log names the channel and feeds[n].
```

`feed_polls_total{outcome="suspicious"}` rising means a feed whose ids change on every
fetch, or one outrunning its window; neither publishes, and the `warn` log says which.

The `transform` label is an id the operator declared, never one a caller typed. A rise
of `transform_requests_total{outcome!="ok"}` usually means a producer changed its
format (`not_list`, and `eval_error` items); `outcome="unlisted"` is someone with a key
probing transforms on a channel they may publish to. Worth a ticket rule, not a page:

```yaml
- alert: WeeboNotifyTransformRefusing
  expr: sum by (transform, outcome) (rate(transform_requests_total{outcome!="ok"}[1h])) > 0
  for: 1h
  labels: { severity: ticket }
  annotations:
    summary: A JSON webhook producer is being refused; `notify-server transform try` a saved body.
- alert: WeeboNotifyTransformSlow
  expr: histogram_quantile(0.99, sum by (le) (rate(transform_eval_seconds_bucket[30m]))) > 0.1
  for: 30m
  labels: { severity: ticket }
```

`grafanaDashboard.enabled` adds one dashboard (connections, publish rate, push
latency and failures, job freshness, dead letters, retention and sync backlog) as a
ConfigMap labelled for the Grafana sidecar.

## Traces

Off unless you ask for them. Name a collector and the server exports spans over
**OTLP/HTTP** (protobuf); with no `[telemetry]` section there is no exporter, no
span processor and no extra thread.

```toml
[telemetry]
otlp_endpoint = "http://collector:4318"  # /v1/traces is appended for you
service_name = "weebo-notify"            # one name per deployment, not per replica
sample_ratio = 1.0                       # 0.0–1.0
trust_inbound_trace_context = false      # continue a caller's traceparent
```

Every key is environment-overridable like the rest of the configuration, so one file
covers every environment: `WNK_TELEMETRY__OTLP_ENDPOINT=http://collector:4318` alone
is enough to switch tracing on.

A publish produces the chain the design asks for — `http` → `publish` (or `upsert`) →
`fanout` → `push`, the last one named by the transport that answered. Span attributes
carry the channel, the notification id and the matched route, and never a title, a
body, a user or a push endpoint: the rule the logs follow applies to spans too.

### Sending your own trace in

With `trust_inbound_trace_context = true` (`WNK_TELEMETRY__TRUST_INBOUND_TRACE_CONTEXT`)
a caller may pass a W3C `traceparent`, and the request continues that trace instead of
starting one — which is how a CI pipeline links its own trace to the notification it
publishes:

```bash
curl -X POST https://notify.example/api/v1/notifications \
  -H "traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01" \
  ...
```

It is **off by default**, because the header comes from whoever calls the API: with it
off, every request starts its own root trace and the header is ignored. Turn it on
where the callers are your own pipelines and services.

<Callout>
  Even when trusted, a caller's `sampled` flag does **not** force recording: a remote
  parent is sampled by `sample_ratio` like a fresh root, so a client that marks every
  request sampled cannot turn a 1 % ratio into 100 % of traces exported. Spans created
  inside the process always follow their local root — a trace with holes in the middle
  is harder to read than no trace.
</Callout>

Spans are flushed on `SIGTERM` before the process exits — otherwise the batch
processor would drop exactly the spans of whatever made you restart it.

## Logs

Structured JSON, and never a payload. Administrative actions land in a separate
append-only audit stream, browsable through `GET /admin/audit` — that is the one
replayed after an incident, and it is not the technical log.
